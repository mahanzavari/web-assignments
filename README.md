پاسخ‌ها را با لحنی روان، دانشجویی و منطبق بر ادبیات فنی و رایج گیت تنظیم کرده‌ام تا دقیقاً شبیه به یک پاسخ‌نامه‌ی تمیز و دست‌نویسِ دانشجو به نظر برسد:

## **پاسخ تمرین Git — مهندسی اینترنت**

---

### **۱.۲ سؤال یک: merge و rebase**

#### **نحوه‌ی ترکیب و شکل تاریخچه:**
* **`git merge`:** 
  وقتی دو شاخه را مرج می‌کنیم، گیت آخرین وضعیت هر دو شاخه را با نقطه‌ی اشتراک آن‌ها (Common Ancestor) می‌سنجد و یک کامیت جدید به نام **Merge Commit** می‌سازد. این کامیت دو والد (Parent) دارد و نقطه‌ی پیوند دو شاخه را نشان می‌دهد.
  * **شکل تاریخچه:** تاریخچه غیرخطی و شاخه‌شاخه باقی می‌ماند. ترتیب زمانی رویدادها دقیقاً همان‌طور که اتفاق افتاده ثبت می‌شود و کاملاً مشخص است که چه زمانی شاخه‌ای منشعب و چه زمانی ادغام شده است.
* **`git rebase`:** 
  به‌جای ساخت کامیت ادغام، پایه‌ی شاخه‌ی ما را جابه‌جا می‌کند. یعنی کامیت‌های اختصاصی شاخه‌ی فعلی را موقتاً کنار می‌گذارد، سرِ شاخه را به نوک شاخه‌ی هدف می‌برد و سپس تک‌تک آن کامیت‌ها را با شناسه‌ها (هش‌های) جدید یکی‌یکی روی پایه‌ی جدید بازنویسی و اعمال (Replay) می‌کند.
  * **شکل تاریخچه:** تاریخچه کاملاً خطی و یک‌دست می‌شود؛ انگار همه‌ی کارها از ابتدا پشت سر هم و بدون هیچ انشعابی روی یک شاخه انجام گرفته‌اند. البته بهای این تمیزی، بازنویسی تاریخچه‌ی کامیت‌ها است.

#### **موقعیت مناسب استفاده و دلیل:**
* **موقعیت برای `merge`:** وقتی می‌خواهیم شاخه‌ی تمام‌شده‌ی یک ویژگی (`feature`) را روی شاخه‌ی اصلی (`main`) اعمال کنیم.
  * *دلیل:* در شاخه‌های عمومی و تیمی نباید تاریخچه بازنویسی شود. وجود کامیتِ مرج مثل یک بسته‌بندی مشخص نشان می‌دهد که این قابلیت کِی، چطور و با چه کامیت‌هایی وارد پروژه شده و در صورت بروز مشکل، بازگرداندن کل آن تغییر آسان‌تر است.
* **موقعیت برای `rebase`:** وقتی روی شاخه‌ی ویژگیِ محلی خودمان کار می‌کنیم و می‌خواهیم آن را با آخرین تغییرات جدید شاخه‌ی `main` به‌روز کنیم (قبل از زدن PR یا مرج نهایی).
  * *دلیل:* تاریخچه‌ی شاخه‌ی ما تمیز می‌ماند و جلوی ثبت کامیت‌های بیهوده مثل `Merge branch 'main' into ...` گرفته می‌شود. چون شاخه هنوز محلی است و کسی از آن استفاده نکرده، بازنویسی آن مشکلی برای هم‌تیمی‌ها نمی‌سازد.

### **۲.۲ سؤال دو: انتخاب بخشی از تغییرات**

#### **مفهوم Hunk:**
در خروجی دستور `git diff`، به هر قطعه یا تکه از خطوط به‌هم‌پیوسته که تغییر کرده‌اند (همراه با چند خط کدِ بدون تغییرِ قبل و بعد آن برای فهم بهتر زمینه)، یک **Hunk** می‌گویند. گیت فایل را به این قطعات تقسیم می‌کند تا بتوان تغییرات را بخش‌بخش بررسی کرد.

#### **بررسی تعاملی و بردن بخشی از تغییرات به Staging:**
برای این کار از دستور `git add` با پرچم پچ (`p-`) استفاده می‌کنیم:
```bash
git add -p README.md
```
گیت فایل را تکه‌تکه (Hunk به Hunk) نشان می‌دهد و می‌پرسد با این بخش چه کنیم. کلیدهای پرکاربرد این‌ها هستند:
* `y`: این تکه به ناحیه‌ی Staging اضافه شود.
* `n`: این تکه نادیده گرفته شود و در working tree باقی بماند.
* `s`: اگر درون یک تکه، چند تغییر با چند خط فاصله وجود دارد، آن را به تکه‌های کوچک‌تر (Split) تقسیم کند تا بتوان دقیق‌تر انتخاب کرد.
* `e`: این بخش را در ادیتور باز کند تا خودمان دستی خط‌ها را دستکاری کنیم.
* `q`: خروج از فرایند.

#### **فایده برای ساخت کامیت‌های منسجم:**
این کار به ما اجازه می‌دهد **Atomic Commits** بسازیم. خیلی اوقات حین کد زدن، هم باگ رفع می‌کنیم، هم متنی را اصلاح می‌کنیم و هم کامنت می‌گذاریم. با `git add -p` می‌توانیم این تغییرات مختلف را از هم تفکیک کنیم و هر کدام را در یک کامیت جداگانه و مشخص قرار دهیم، به‌جای اینکه یک کامیت شلوغ و درهم داشته باشیم. این کار خواندن تاریخچه و پیدا کردن خطاها را بسیار راحت می‌کند.

### **۳.۲ سؤال سوم: یافتن منشأ خطا**

#### **نحوه‌ی کار `git bisect`:**
این ابزار بر اساس **جست‌وجوی دودویی (Binary Search)** کار می‌کند. اگر بین نسخه‌ی سالم و خراب ۱۰۰ کامیت فاصله باشد، به‌جای تست تک‌تک آن‌ها، گیت وسط بازه را انتخاب می‌کند. اگر سالم بود، نیمه‌ی اول را کنار می‌گذارد و سراغ نیمه‌ی دوم می‌رود؛ و اگر خراب بود برعکس. با این روش در حدود $\log_2(n)$ مرحله کامیت مقصر پیدا می‌شود.

#### **مراحل استفاده:**
۱. شروع فرآیند:
   ```bash
   git bisect start
   ```
۲. علامت زدن کامیت خراب فعلی:
   ```bash
   git bisect bad
   ```
۳. معرفی آخرین کامیتی که مطمئنیم برنامه در آن درست کار می‌کرد:
   ```bash
   git bisect good v1.2
   ```
۴. گیت به‌طور خودکار کامیتی در میانه‌ی تاریخچه را Checkout می‌کند. پروژه را تست می‌کنیم:
   * اگر باگ وجود داشت: می‌زنیم `git bisect bad`
   * اگر باگ نبود و همه چیز سالم بود: می‌زنیم `git bisect good`
۵. این روند را تکرار می‌کنیم تا در نهایت گیت پیام دهد که فلان کامیت اولین جایی بوده که باگ را وارد کرده است.
۶. در انتها برای برگشت به شاخه و وضعیت قبلی:
   ```bash
   git bisect reset
   ```

#### **مثال و فایده:**
فرض کنید در نسخه‌ی جدید، دکمه‌ی پرداخت از کار افتاده اما می‌دانیم ماه قبل در تگ `v2.0` درست کار می‌کرد و بین آن زمان تا الان ۲۰۰ کامیت ثبت شده است. تست تک‌تک ۲۰۰ کامیت ساعت‌ها زمان می‌برد، اما با `git bisect` نهایتاً با ۷ تا ۸ بار تست کردن، دقیقاً مشخص می‌شود کدام کامیت و چه کدی دکمه را خراب کرده است.

### **۴.۲ سؤال چهارم: بررسی تغییرات پیش از کامیت**

#### **۱. دستورهای بررسی و تفاوت تغییرات:**
* مشاهده‌ی وضعیت کلی فایل‌ها:
  ```bash
  git status
  ```
* دیدن تغییراتی که هنوز به staging اضافه **نشده‌اند** (تفاوت Working Directory با Staging):
  ```bash
  git diff README.md
  ```
* دیدن تغییراتی که در staging قرار دارند و آماده‌ی کامیت هستند (تفاوت Staging با آخرین کامیت یا HEAD):
  ```bash
  git diff --staged README.md
  # یا معادل آن: git diff --cached README.md
  ```
* **تفاوت دو دسته:** تغییرات staged مواردی هستند که با `git add` نشانه‌گذاری شده‌اند و گیت از آن‌ها در کامیت بعدی عکس (snapshot) می‌گیرد. اما تغییرات unstaged صرفاً ادیت‌هایی روی دیسک هستند که هنوز به گیت معرفی نشده‌اند و در صورت کامیت زدن، نادیده گرفته می‌شوند.

#### **۲. نتیجه‌ی اجرای کامیت معمولی (بدون `a-`):**
تنها تغییراتِ بخش اول که قبلاً Staged شده بودند در کامیت جدید ثبت می‌شوند. ویرایش‌های بعدی که بعد از دستور `add` روی فایل انجام داده‌اید، همان‌طور Unstaged در Working Directory باقی می‌مانند.  
*دلیل:* در گیت، دستور `git commit` محتوای ناحیه‌ی Staging (Index) را ثبت می‌کند، نه وضعیت جاری فایل‌ها روی هارددیسک را.

#### **۳. نادیده گرفتن پوشه‌ی `tmp/` و فایل‌های Tracked:**
* **تنظیم:** کافی است یک خط زیر را درون فایل `.gitignore` در ریشه‌ی پروژه اضافه کنیم:
  ```gitignore
  tmp/
  ```
* **آیا برای فایل‌های Tracked قبلی کافی است؟** خیر.  
  *توضیح:* قانون‌های `.gitignore` فقط روی فایل‌های جدید و ردیابی‌نشده (Untracked) اعمال می‌شوند. اگر فایلی از قبل Tracked شده باشد، گیت به تغییراتش گوش می‌دهد و کاری به `.gitignore` ندارد. برای حل این مشکل، باید ابتدا آن را از حافظه‌ی گیت خارج کنیم (بدون اینکه از روی سیستم پاک شود):
  ```bash
  git rm -r --cached tmp/
  ```
  سپس این تغییر را کامیت کنیم تا از آن به بعد `.gitignore` روی آن پوشه اثر بگذارد.

### **۵.۲ سؤال پنجم: رفع merge conflict در کار گروهی**

#### **۱. علت بروز Conflict:**
این اتفاق به این دلیل افتاده که هر دو نفر کار را از یک نقطه‌ی مشترک شروع کرده‌اند و **دقیقاً روی همان خط یکسان** از فایل `README.md` دو متن متناقض نوشته‌اند. گیت نمی‌تواند حدس بزند کدام جمله مقصود نهایی تیم است، بنابراین متوقف می‌شود تا انسان تصمیم بگیرد.  
*آیا هر تغییری تداخل می‌دهد؟* خیر. اگر دو نفر دو فایل مختلف یا حتی خطوط متفاوتی از یک فایل را ویرایش کنند، گیت تغییرات هر دو را خودکار ادغام می‌کند.

#### **۲. شناسایی فایل‌ها و نشانگرها (Markers):**
* با اجرای دستور `git status`، فایل‌های دارای مشکل با برچسب `both modified` نشان داده می‌شوند.
* محتوای فایل هم با این نشانگرها علامت می‌خورد:
  * `<<<<<<< HEAD`: شروع کدی که در شاخه‌ی فعلی ما (اینجا `main`) قرار دارد.
  * `=======`: خط جداکننده‌ی دو نسخه.
  * `>>>>>>> feature-description`: پایان کدی که از شاخه‌ی دیگر آمده است.

#### **۳. مراحل حل تداخل و حفظ هر دو تغییر:**
۱. فایل `README.md` را باز می‌کنیم.
۲. علامت‌های `<<<<<<<`، `=======` و `>>>>>>>` را کاملاً با دست پاک می‌کنیم و متن‌ها را طوری پشت سر هم مرتب و ویرایش می‌کنیم که هر دو مفهوم با لحنی درست در فایل بمانند.
۳. **اطمینان از تمیز بودن فایل:** با دستور زیر فایل را بررسی می‌کنیم تا اثری از علامت‌ها نمانده باشد:
   ```bash
   git diff
   # یا اطمینان از نبود علامت‌ها:
   grep -E "^(<<<<<<<|=======|>>>>>>>)" README.md
   ```
۴. فایلِ درست‌شده را به Staging می‌بریم:
   ```bash
   git add README.md
   ```
۵. با اجرای دستور commit، پیام ادغام را نهایی می‌کنیم:
   ```bash
   git commit
   ```

#### **۴. لغو عملیات Merge:**
اگر وسط کار پشیمان شدیم، با دستور زیر همه چیز را لغو می‌کنیم و شاخه به حالت تمیز قبل از مرج برمی‌گردد:
```bash
git merge --abort
```

### **۶.۲ سؤال ششم: انتخاب روش مناسب برای بازگرداندن تغییرات**

#### **۱. لغو تغییرات محلی در فایل `notes.txt` (حالت Unstaged):**
* **دستور:**
  ```bash
  git restore notes.txt
  # یا دستور قدیمی‌تر:
  git checkout -- notes.txt
  ```
* **دلیل:** دستور `restore` دقیقاً برای بازگرداندن فایل‌های درون Working Tree بدون دستکاری بقیه‌ی پروژه است.
* **اثرات:**
  * *Working Tree:* تمام دستکاری‌های اخیر روی `notes.txt` دور ریخته می‌شود و فایل برمی‌گردد به آخرین وضعیتی که در Staging/Commit داشت. بقیه‌ی فایل‌ها دست‌نخورده می‌مانند.
  * *Staging Area:* هیچ تغییری نمی‌کند.
  * *تاریخچه‌ی کامیت‌ها:* هیچ تغییری نمی‌کند.

#### **۲. خارج کردن `notes.txt` از Staging با حفظ ادیت‌ها روی دیسک:**
* **دستور:**
  ```bash
  git restore --staged notes.txt
  # یا روش سنتی:
  git reset HEAD notes.txt
  ```
* **دلیل:** پرچم `--staged` فقط ایندکس گیت را به آخرین کامیت برمی‌گرداند و کاری به فایل‌های روی دیسک ندارد.
* **اثرات:**
  * *Working Tree:* کدهایی که نوشتید کاملاً حفظ می‌شوند، فقط برچسبِ Staged از روی فایل برداشته می‌شود و در خروجی `git status` به رنگ قرمز (تغییرات Unstaged) درمی‌آید.
  * *Staging Area:* فایل از این ناحیه خارج می‌شود.
  * *تاریخچه‌ی کامیت‌ها:* هیچ تغییری نمی‌کند.

#### **۳. برگرداندن کامیت اشتباه روی شاخه‌ی مشترک `main`:**
* **دستور:**
  ```bash
  git revert <bad-commit-hash>
  git push origin main
  ```
* **دلیل انتخاب Revert و خطر Force Push:**  
  وقتی کدی روی شاخه‌ی اشتراکی مثل `main` رفته و دیگران آن را pull کرده‌اند، **به هیچ وجه نباید** از `git reset --hard` و بعد `push --force` استفاده کرد؛ چون تاریخچه پاک می‌شود و شاخه‌ی گیت‌هاب با تاریخچه‌ی سیستم هم‌تیمی‌ها ناسازگار (Diverged) خواهد شد. این کار باعث از بین رفتن کارهای دیگران و خطاهای شدید در همگام‌سازی می‌شود.  
  اما `git revert` یک کامیتِ رو‌به‌جلو می‌سازد که کارش برعکس کردن تغییرات آن کامیت معیوب است.
* **اثرات:**
  * *Working Tree:* تغییرات مخرب کامیت قبلی خنثی شده و کد به حالت سالم درمی‌آید.
  * *Staging Area:* بعد از انجام کامیت، تمیز (Clean) خواهد بود.
  * *تاریخچه‌ی کامیت‌ها:* تاریخچه سالم می‌ماند، کامیت اشتباه حفظ می‌شود و یک کامیت جدید (Revert Commit) بعد از آن ثبت می‌گردد تا تاریخچه دستکاری نشود.
